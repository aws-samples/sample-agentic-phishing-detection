# Agentic Phishing URL Detection on Amazon Bedrock AgentCore

**Paste a link and get an explained phishing verdict in about 20 seconds.** Three specialist agents check the link, the page and the page's code at the same time in an isolated cloud browser. An orchestrator agent weighs their evidence, gives you the verdict first and then writes a plain-language report. Everything runs in your own AWS account.

## What it does

| At a glance | |
| --- | --- |
| **What**          | A serverless phishing URL triage service: a web app and a SigV4-signed API that return a verdict, a risk score, the evidence and a plain-language report |
| **Who it is for** | Security and trust and safety teams triaging reported links, and platforms that want a pre-publish gate that holds risky links for review                |
| **How**           | Three specialist agents (Claude Sonnet 5.5) check one thing each, in parallel; an orchestrator (Claude Opus 5.5) judges their findings                   |
| **Runs in**       | Your own AWS account. One AWS CDK command deploys it, one tears it down                                                                                  |

- **Scan one URL** in the web app or with one API call.
- **Scan many URLs at once**: up to 200 from a CSV in the web app. Through the API, up to 1,000 from a CSV or 50 as JSON.
- **See the evidence**: a screenshot of the page, how the link redirected, what the page's code does, the domain's registration facts, and a report.
- **Act on the verdict first**: it appears while the full report is still being written.
- **Answer dead links fast**: a page that answers HTTP 404, or a host that is down, gets a fixed answer without an orchestrator call.
- **Track usage** on the Insights page: volume, verdicts, scan time, tokens and cost.

| Verdict      | Meaning                                                                                                                                           | Action |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------- | ------ |
| `phishing`   | Strong evidence of phishing                                                                                                                       | block  |
| `suspicious` | Some risk signals, not conclusive. Also the most a scan can say when a provider warning hid the real page                                         | warn   |
| `legitimate` | No meaningful risk found                                                                                                                          | allow  |
| `unknown`    | No usable evidence                                                                                                                                | warn   |
| `error_404`  | The URL returned HTTP 404, so there was no page to judge (risk 10)                                                                                | allow  |
| `site_down`  | The host does not resolve, refuses the connection, answers HTTP 410 or redirects to a dead host (risk 10). A certificate error is never Site down | allow  |

### How this differs from third-party URL scanners

Rather than relying on a hosted service's blocklists or past reports, this sample analyzes each URL directly, in your own AWS account:

- **Live content analysis.** For each URL, it opens the page in an isolated Amazon Bedrock AgentCore Browser, and three specialist agents examine the link and the live page: its address and domain registration, its visual branding and on-page copy, and its underlying code (forms, scripts, where data is sent). An orchestrator then returns a verdict with a risk score and a confidence. Because it judges the page itself, it can assess a newly created site that has no history yet.
- **Customer-managed: it runs in your own AWS account.** You deploy and operate it, and scan records and evidence are stored only in your account. To analyze a URL, the sample visits the page and queries public domain-registration (RDAP) and web-search services. You choose the deployment Region and the models; the default cross-Region inference profiles may route model requests to other Regions, and the edge stack always deploys to `us-east-1`. You set how long scans are kept (`-c retentionDays`); other retention periods are set in the CDK code you deploy. IAM controls who may call the API, and Amazon Cognito who may use the web app. This suits URLs you would rather not submit to an outside service. Private and internal addresses are blocked by design.

The trade-off is deliberate: this is sample code that performs per-scan AI analysis you run and pay for, not a managed, pre-populated reputation database. Verdicts are advisory; have a person review any verdict with a low confidence score.

## How it works

![Architecture: users and API clients reach API Gateway directly or through CloudFront and AWS WAF; the API queues each scan on Amazon SQS for the worker Lambda. The worker pre-checks the URL on the tools server and, at the same time, invokes url_analyst, brand_visual and code_analyst (step 3). brand_visual and code_analyst each capture the page through their own copy of the tools server (step 4), which drives AgentCore Browser (step 5). The worker then asks the orchestrator model on Amazon Bedrock for the verdict and the report (step 6). The supporting services row, including the standby Harness path and the opt-in Agent Registry, has no lines](docs/architecture.png)

1. **You submit a URL** in the web app or through the API. It is checked by a guardrail, stored and queued.
2. **The worker picks it up** from Amazon SQS, at most 25 scans at once by default.
3. **A pre-check and the three specialists start together.** The pre-check opens the URL once; a page that answers HTTP 404, or a site that is down, ends here with a fixed answer. The specialists run on AgentCore Runtime.
4. **The page specialists capture the page** through their own copy of the tools server,
5. **in AgentCore Browser**, an isolated browser that AWS runs for you, so the page never loads on your machine.
6. **The orchestrator** (Claude Opus 5.5 on Amazon Bedrock) judges the three findings and returns the verdict, then writes the report, which an Amazon Bedrock guardrail screens. When all three specialists agree with high confidence that a page is legitimate, the verdict is stored without the orchestrator's verdict turn.

| Agent                                       | Checks                                                                            | Model             |
| ------------------------------------------- | --------------------------------------------------------------------------------- | ----------------- |
| [orchestrator](docs/agents/orchestrator.md) | Holds the findings to a quality bar, gives the verdict, then writes the report    | Claude Opus 5.5   |
| [url_analyst](docs/agents/url_analyst.md)   | Look-alike domains, risky hosting, domain age, where the link redirects           | Claude Sonnet 5.5 |
| [brand_visual](docs/agents/brand_visual.md) | Brand impersonation, fake sign-in pages, scare copy, the brand's official website | Claude Sonnet 5.5 |
| [code_analyst](docs/agents/code_analyst.md) | Credential forms posting elsewhere, keyloggers, obfuscation                       | Claude Sonnet 5.5 |

> [!NOTE]
> **Two orchestration paths.** The default is the fast path above. `-c directOrchestration=false` puts the orchestrator on AgentCore Harness, which calls the specialists through a [dispatcher](docs/agents/dispatcher.md) and AgentCore Gateway, keeps a Harness trace and may ask one specialist a second time. Turning only that flag off measured about 8 to 11 s slower at the median and about 47% more model cost per scan ([evaluation.md](docs/evaluation.md#each-latency-flag-on-its-own-2026-11-03)); it is the only latency flag with a clear measured effect on its own. Every step and permission of both paths: [docs/architecture.md](docs/architecture.md).

## Quick start

You need AWS credentials, Node.js 22, Python 3.13 with [uv](https://docs.astral.sh/uv/), Finch or Docker with ARM64 builds, and Amazon Bedrock access to Claude Opus 5.5 and Claude Sonnet 5.5 in your Region. The API example also needs `awscurl` (`uv tool install awscurl==0.45`) and `jq`.

```bash
git clone https://github.com/aws-samples/sample-agentic-phishing-detection.git
cd sample-agentic-phishing-detection
uv sync --all-packages
export AWS_REGION=<your-region> AWS_PROFILE=<your-profile>   # every command below uses this account
uv run python scripts/preflight.py --profile "$AWS_PROFILE" --region "$AWS_REGION"   # checks models, AgentCore, bootstrap, tools

npx aws-cdk@2.1143.0 bootstrap aws://<account-id>/$AWS_REGION aws://<account-id>/us-east-1   # once per account; skip if preflight passes it
cd infra && export CDK_DOCKER=finch   # or docker
npx aws-cdk@2.1143.0 deploy --all -c owner=<team or alias>   # 8 to 16 minutes the first time; add --require-approval never in CI
```

Then open the `WebUrl` stack output, register with your email, sign in with the temporary password Cognito emails you (no inbox, for example a demo user: see [getting-started](docs/getting-started.md#create-a-user-without-email)), and scan `https://www.iana.org/domains/reserved`: expect **Legitimate**.

`owner` becomes the `Owner` tag on every resource, so cost shows up against you in Cost Explorer. A small edge stack goes to `us-east-1` because AWS requires the AWS WAF web ACL for CloudFront there. Step by step, with every check: [docs/getting-started.md](docs/getting-started.md).

## Use the API

The API is the same one the web app uses. Every route except `GET /health` needs an AWS SigV4 signature. Cognito gates only the web console, not the API. Attach the `ApiInvokePolicyArn` stack output to the IAM role or user you call with, then:

```bash
STACK=${STACK:-PhishTriageAgentic}   # or <Name>TriageAgentic if you deployed with -c appName=<name>
API=$(aws cloudformation describe-stacks --stack-name "$STACK" \
  --query "Stacks[0].Outputs[?OutputKey=='ApiUrl'].OutputValue" --output text); API=${API%/}
id=$(awscurl --service execute-api --region "$AWS_REGION" -X POST "$API/scan" \
  -H 'Content-Type: application/json' -d '{"url": "https://example.com"}' | jq -r .scan_id)
until awscurl --service execute-api --region "$AWS_REGION" "$API/scans/$id" > scan.json &&
  jq -e '.status == "FAILED" or .status == "COMPLETE"' scan.json > /dev/null; do sleep 3; done
jq '{status, verdict: .verdict.verdict, risk: .verdict.risk_score, action: .verdict.action, page_observed: .verdict.page_observed}' scan.json
```

A pre-publish gate holds a link for a person to review when the scan `FAILED`, the action is `block` or `warn`, the risk is 70 or more, or `page_observed` is `false`; otherwise it publishes. The verdict is advisory: a gate should hold a risky link for review, not reject it on its own. Batches, idempotent retries, lookups and a Python gate: [docs/getting-started.md](docs/getting-started.md#test-the-api-a-pre-publish-gate) and [docs/api.md](docs/api.md).

## Security

- **Signed access only.** The API takes SigV4 (IAM) calls only; the web console signs in with Amazon Cognito (optional or required TOTP MFA) behind CloudFront and AWS WAF.
- **The page never runs on your machine.** It opens in AgentCore Browser; the agents do not type, submit forms or solve bot checks. Every outbound request goes through an SSRF guard.
- **Guardrails both ways.** Amazon Bedrock Guardrails check every submitted URL and every report; URLs in model-written text are defanged (`hxxps://example[.]com`).
- **Encrypted, scoped and tagged.** AWS KMS customer managed keys on tables, buckets, queues and logs; one IAM role per component, with every wildcard listed and explained in [security.md](docs/security.md#iam).

Details: [security.md](docs/security.md), [threat model](docs/threat-model.md), [responsible AI](docs/responsible-ai.md). To report a security issue, see [SECURITY.md](SECURITY.md).

## Clean up

> [!WARNING]
> The stacks cost about $14 to $15 per month even when you run no scans (see [Cost](#cost)). Delete them when you are done. This deletes the stored scans and every Cognito user.

```bash
cd infra
npx aws-cdk@2.1143.0 destroy --all
# a second copy deployed with -c appName=<name>: pass the same flag
npx aws-cdk@2.1143.0 destroy --all -c appName=<name>
```

Then confirm nothing tagged for this sample is left. Every copy shares the `Project` tag, so once you have destroyed every copy, both commands should return an empty `ResourceTagMappingList`:

```bash
aws resourcegroupstaggingapi get-resources --tag-filters Key=Project,Values=phish-triage --region "$AWS_REGION"
aws resourcegroupstaggingapi get-resources --tag-filters Key=Project,Values=phish-triage --region us-east-1
```

A few things stay behind and are yours to remove (a log group created at run time, the CDK bootstrap stacks, container images in the CDK asset repository); `-c environment=prod` keeps the data stores. See [docs/deploy.md](docs/deploy.md#clean-up).

## FAQ

### Why three specialists and an orchestrator?

Each specialist looks at one thing with a short, focused prompt, so its evidence is easy to check. The orchestrator is the judge: it checks the findings, spots what one agent missed and settles disagreements. The specialists run at the same time, so a scan waits for about the slowest of the three, not their sum.

### Does it visit the page, or click anything?

It opens the page in Amazon Bedrock AgentCore Browser, an isolated browser that AWS runs for you, so the page never loads on your machine. It does not type, submit forms or solve bot checks. It clicks one thing only: on a Cloudflare phishing or malware warning, the warning's own proceed button, once, and only when Cloudflare has enabled it. When the browser cannot load a page, `code_analyst` reads its raw HTML once with a plain GET through the same URL safety guard, and never runs it.

### What does "Page not observed" mean?

The browser never saw the site's real page: a provider warning (such as Cloudflare's "Suspected Phishing" page), a bot check, a block page or a failed capture stood in front of it, or only its raw HTML was read. When a provider warning hid it, the scan is held at Suspicious (risk at most 69, action `warn`): the warning is strong evidence but it is a third party's opinion. In every case `page_observed` is `false`. Send these to a person.

### Why does the verdict appear before the report?

The orchestrator answers in two calls. The first returns the compact verdict, which the app shows at once. The second writes the report, which is screened and stored afterwards. A failed report never changes the verdict.

### What is Agent Registry for, and why is it off?

AWS Agent Registry is a catalog of agents and MCP servers. With `-c agentRegistry=true` the stack registers its five MCP servers and the orchestrator looks them up once per scan, which shows how a team could govern and discover agents. It does not route calls and the scan works the same without it, so it is off by default. It runs on the Harness path.

### Can I use other models?

Yes. Set `-c orchestratorModel=<id>` or `-c specialistModel=<id>` to any Amazon Bedrock inference profile you have access to, then redeploy. Every `global.`, `us.`, `eu.`, `apac.`, `au.` and `jp.` profile of the priced models is costed; a model with no price shows its cost as unknown. The measured results apply only to the default models.

### Does it store my URLs, and for how long?

Yes, so you can see results and history. Scans and batches are deleted after `retentionDays` (default 90), screenshots and page captures after 30 days, uploaded CSV files after 1 day. Only you can read your own scans.

### Can I keep data in the US only?

The orchestrator uses a `us.` inference profile. The specialists default to a `global.` profile, which can route requests to other Regions. Set `-c specialistModel=` to a `us.` profile available to you and deploy to a US Region.
